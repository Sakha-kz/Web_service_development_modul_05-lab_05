# Модуль 05. Лабораторная работа (СРСП): Клиентское приложение ProductClient для управления товарами
## Архитектурные решения, реализация CRUD с HttpClient и ответы на контрольные вопросы

---

### Архитектурный разбор и организация клиент-серверного взаимодействия

#### 1. Роль и место клиентского приложения
В современной распределенной разработке пользовательские интерфейсы (Web MVC, SPA, мобильные клиенты) отделены от бизнес-логики и хранилищ данных.
Приложение **`ProductClient`** выступает потребителем (Consumer / Client) RESTful веб-сервиса:
* Контроллер `ProductController` отвечает за отображение представлений Razor и обработку действий пользователя.
* Сервис `ProductApiService` абстрагирует сетевые вызовы и преобразует HTTP-ответы в строго типизированные модели C#.
* Вся коммуникация с Web API происходит строго по протоколу HTTP с передачей данных в формате JSON.

#### 2. Преимущества использования `IHttpClientFactory`
* **Предотвращение исчерпания сетевых сокетов:** Фабрика управляет пулом соединений и жизненным циклом `HttpMessageHandler`.
* **Автоматическое отслеживание изменений DNS:** В отличие от статического `HttpClient`, фабрика обновляет внутренние хэндлеры каждые 2 минуты.
* **Централизованная настройка:** Базовый адрес (`BaseAddress`) и общие заголовки (`Accept: application/json`) регистрируются один раз в `Program.cs`:
  ```csharp
  builder.Services.AddHttpClient("ProductApi", client =>
  {
      client.BaseAddress = new Uri(builder.Configuration["ApiSettings:BaseAddress"] ?? "http://localhost:5000/");
      client.DefaultRequestHeaders.Add("Accept", "application/json");
  });
  ```

#### 3. Реализация CRUD-операций через HttpClient
* **`GET /api/products` (Получение всех товаров):**
  Отправка `client.GetAsync("api/products")`. При успешном ответе тело JSON десериализуется методом `response.Content.ReadFromJsonAsync<List<Product>>()`.
* **`GET /api/products/{id}` (Получение одного товара):**
  При статусе `404 Not Found` метод возвращает `null`, а контроллер выводит пользователю информационное сообщение «Товар не найден».
* **`POST /api/products` (Добавление товара):**
  Используется метод расширения `client.PostAsJsonAsync("api/products", product)`. При статусе `201 Created` товар считается успешно созданным. При статусе `400 Bad Request` текст ошибки извлекается и отображается в форме.
* **`PUT /api/products/{id}` (Обновление товара):**
  Отправка `client.PutAsJsonAsync($"api/products/{product.Id}", product)`. Обновляет наименование, описание, цену и количество.
* **`DELETE /api/products/{id}` (Удаление товара):**
  Отправка `client.DeleteAsync($"api/products/{id}")`. При `200 OK` товар удаляется из каталога.

#### 4. Сценарий демонстрации работы (Часть 10)
1. **Запуск:** Запустить приложение командой `dotnet run`. Одновременно запускается Web API и клиентский MVC-интерфейс.
2. **Получение списка:** Открыть главную страницу `http://localhost:5000/`. Загружается список из 3 начальных товаров (Notebook, Mouse, Keyboard).
3. **Получение по ID:** Нажать «Инфо» на товаре #1 (Notebook). Отображаются детальные характеристики. Проверить несуществующий ID (например, `/Product/Details/999`) — отображается сообщение об ошибке 404.
4. **Добавление товара:** Нажать «Добавить товар», заполнить форму (Монитор 27", 180 000 ₸, 7 шт.) и нажать «Добавить товар». Проверить появление товара в списке.
5. **Изменение товара:** Нажать «Изменить» у созданного товара, изменить цену или количество, сохранить и убедиться в обновлении таблицы.
6. **Удаление товара:** Нажать «Удалить», подтвердить действие в модальном окне. Убедиться, что товар исчез из списка.

### Ответы на контрольные вопросы

#### 1. Чем вызов Web API из клиентского приложения отличается от прямого обращения к базе данных?
* **Инкапсуляция и безопасность:** Клиент не имеет прямого доступа к БД и строкам подключения. Вся логика валидации и безопасности находится на стороне API.
* **Слабая связанность:** База данных может быть изменена или перенесена без изменения клиента, пока API сохраняет стабильный контракт.
* **Кроссплатформенность:** Один и тот же Web API могут одновременно использовать Web-клиенты, мобильные приложения iOS/Android и сторонние сервисы.

#### 2. Какие преимущества дает разделение на `IProductApiService` и `ProductController`?
Соблюдается принцип единой ответственности (Single Responsibility Principle):
* `ProductController` отвечает исключительно за обработку веб-запросов пользователя и возврат представлений Razor.
* `ProductApiService` отвечает за сетевое взаимодействие, сериализацию/десериализацию JSON и обработку HTTP-статусов.
* Это позволяет легко протестировать контроллер с помощью Mock-объекта `IProductApiService` без реальных сетевых вызовов.

#### 3. Как правильно передавать данные сложных объектов в запросах POST и PUT?
Данные сериализуются в формат JSON и передаются в теле HTTP-запроса (`HttpContent` / `StringContent` с `MediaType: application/json`). В современном .NET для этого используется метод `PostAsJsonAsync` или `PutAsJsonAsync` из пространства имен `System.Net.Http.Json`.

#### 4. Что происходит при возникновении ошибки 500 на стороне Web API и как клиент должен ее обрабатывать?
Статус `500 Internal Server Error` означает сбой или необработанное исключение на сервере. Клиент должен перехватить этот код через проверку `response.StatusCode == HttpStatusCode.InternalServerError`, залогировать инцидент с помощью `ILogger` и уведомить пользователя о временной технической ошибке, не допуская аварийной остановки клиентского приложения.
